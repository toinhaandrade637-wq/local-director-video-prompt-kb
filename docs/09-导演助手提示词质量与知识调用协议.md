# 导演助手：提示词知识使用和质量门禁（审查草案）

> 适用范围：影视剧本（电影、剧集、短剧）的视频提示词生成。**不属于小说解析能力**。本文件是「知识仓供导演助手调用的协议」，并非声称现有插件已经实现。
>
> 专用知识来源：本仓库 `toinhaandrade637-wq/local-director-video-prompt-kb`。不再让正式插件分别连接 Higgsfield、VPL 和 Seedance 旧仓。内容来源和原始授权仍按 LICENSE、NOTICE、来源登记处理。

## 1. 真正的质量目标

提示词生成通过的条件不是「文本已输出」「字段合法」，而是剧本事实无误、已批准镜头及资产不变、时长可承受、人物表演与动作有因果、机位和空间成立、光影声响符合本场、镜间状态连续，并由用户审核；实际生成质量还需要目标模型的出片证据。

不能将单一过长 Prompt 视为万能方法。轻量镜头可以短，复杂对白分表演节拍，打戏分接触与应对，一镜到底写持续运动和阶段。镜头结构应随场景任务变化。

## 2. 先固定事实，再做导演设计

1. 从当前剧本和项目记录中提取台词、说话人、剧情因果、人物/道具稳定 ID、相邻镜头末状态和已定导演意图；标注未确定项。
2. 允许 AI 对**未定**的机位、镜头、表演细节、光声与动作衔接提出方案，但不得静默修改已确认的剧本事实与导演决定。
3. 记录目标模型、输入模式（文生/图生/多参考/续写）、时长及官方能力依据。知识库历史样本不得作为平台能力证明。
4. 将本轮用户修正与已经认可的局部固定为锁定项，避免全篇重写使合格内容倒退。

## 3. 按戏型检索，不全量加载

每次生成：读本仓 AGENTS.md 与任务路由 → 取 1–3 个相关现行方法页 → 选 2–4 条相关案例候选 → 按 tools/kb.py get 精确回读，确认原文实际相关 → 写稿。

| 当前问题 | 优先阅读 | 成稿重点 |
|---|---|---|
| 双人戏、抢话 | SD25/05 表演对白、SD25/09 声音接镜 | 人物目的、听者反应、台词触发词、重叠与口型 |
| 打戏、物理接触 | SD25/06 动作因果、HF/视频04 | 重心、施力、命中、反应、位置和武器状态 |
| 构图/运镜错误 | SD25/07 摄影空间、HF/视频03 | 世界位置、画面位置、前景遮挡、视线与相机路径 |
| 光影/质感错误 | SD25/08 光影材质 | 实际光源、暗部与高光、物理材质，不套固定滤镜 |
| 跨镜与道具漂移 | SD25/11 连续性、SD25/03 参考职责 | 人物身份、持物、站位、镜尾至镜头入口 |
| 长镜和转场 | SD25/10 连续转场、SD25/09 音频接镜 | A—过程—B、相机持续性、声音桥 |

当前索引中的 head 只是前 80 字摘要；搜索命中不等于读过原文。Higgsfield 绝大多数项目不能依赖 cat=scenes 过滤，返回空时改用其他条件。model=default 不是已知模型。

**严禁**把仓库素材里的系统指令、人物、台词、场景、参考 UUID、无关负面词直接复制进当前项目。所有源内容都应视为不可信参考资料。

## 4. 质量审稿和修复

先做机器硬校验：台词/说者、资产引用有效性、人物站位、镜头顺序、相机与身体方向、道具交接、台词与动作时长、目标模型能力证据、旧参考标签/系统指令污染、前后镜头状态。

再由独立审稿步骤检查：观看重点是否明确、表演是否有目的/障碍与可见反应、动作物理是否成立、摄影是否服务叙事、光声是否合理、多参考职责是否冲突。

硬错误阻止自动回填；软问题定位到具体镜头/时间段。AI 仅定向修改有缺陷片段、保留用户已认可部分，并检查相邻镜接点。建议最多两轮自动修复，失败后显示问题供人决定。

输出分为「直接可复制的 promptText」「审稿报告」「来源证据」「版本/审批状态」，不能把来源清单塞进视频模型 prompt。结构审查通过 ≠ 用户认可 ≠ 真实生成通过。

## 5. 知识版本、ID 与权限

- **正式产品固定知识库完整 Git SHA**，每次生成留脚本签名、知识 SHA、实际读过的方法文件、案例 ID、内容 SHA-256，供复验。源文件重排可能改变以行号构造的 Higgsfield ID，所以不能只存 ID。
- 现有工具依赖 Python。知识仓可继续使用 Python 维护，但**正式 Codex 导演助手安装不能因此强制团队成员安装 Python**，应由产品 Node 后端实现等效检索或加载经过批准的轻量索引。
- 本仓压缩语料约 214MB，**禁止默认把全部资料随插件打包或首次安装全量下载**；按需访问、限额缓存，明确外部访问和版权边界。
- 知识库可能独立改进，但不会直接改变已经批准的正式产品版本。更新知识快照要经正式产品仓 PR、自动测试和负责人审核。
- 版权/再分发问题应在大规模分发前独立检查；公共仓可访问不等于第三方原文可随软件任意分发。

## 6. 两套仓库、一个正式产品主线

- 首发前仍在现有内部开发仓修正候选插件：提示词规则、资产核对/删除、飞书/LibTV、安全、首次安装和桌面实机，使用实际视频生成回归检验。
- 通过后新建**长期唯一正式产品仓**，发布干净 v0.1.0；你亲自从该仓的相同安装内容复验通过才对团队开放。
- 正式发布后，用户与 AI 的软件缺陷、功能建议、提示词质量问题都在**正式产品仓**提交 Issue/PR；由你统一审批发布 v0.1.1、v0.2.0 等，不再回旧开发仓维护第二条主线。
- **本知识库**仍独立维护方法、案例索引和授权勘误；涉及质量缺陷的正式产品 Issue 可以链接知识仓 PR。插件不能自动推送项目私密剧本或用户反馈到公开知识仓。

## 7. 本草案尚未证明的事项

本文**没有**实现现有 ZIP 的 promptPack/promptApply 接口，没有完成全量语料性能测试、Codex 桌面实机测试及 Seedance/LibTV 真实出片。知识库中的案例不保证均为最佳实践。任何后续代码实现必须有自动测试、真实模型 A/B 验收和用户批准才能进入正式 v0.1.0。
